# R1Shop 旧后台迁移与业务验收矩阵

## 1. 目的与范围

本文把旧 `shop-admin-ui` 中实际存在的后台页面、按钮权限、API 调用和业务流程转换为 MSS 1.3.7 重构的实施边界与验收基线。目标不是复制旧 Vue 页面，而是在保留 MSS Admin 原生系统功能的前提下，让新租户平台和商城管理平台直接兼容存量业务表及其数据语义。

本轮盘点的量化基线如下：

| 项目 | 数量 | 说明 |
| --- | ---: | --- |
| 存量业务数据库表 | **54 张表** | 由旧后端模型清单确定，并与开发 TimescaleDB 的 `public` schema 做了只读列/主键交叉检查；生产数据仍保持只读，索引、约束和逐表数据验收须在迁移演练中完成 |
| 旧后台业务路由挂载 | 59 个 | 去除登录、404 和 Dashboard 后的运行时业务路由挂载数，部分新增/编辑路由复用同一组件 |
| 旧后台唯一业务视图 | 54 个 | 与“54 张表”只是数字巧合，两者不是一一对应关系 |
| 旧业务 HTTP 请求 | **185 个** | `user.js` 4 个、`tenant.js` 51 个实际请求、`app-admin.js` 130 个；另有 1 个函数别名，不重复计数 |
| 旧系统平台权限（历史来源） | 4 组 / 12 页 / 36 按钮 | 旧前端把租户、中央物流、中央支付、中央商品放在系统平台；此行只记录来源事实 |
| 旧系统商城权限（历史来源） | 13 组 / 37 页 / 135 按钮 | 商城商品、订单、客户、营销、财务、进销存等 |
| 新租户平台权限目标 | 2 组 / 4 页 / 12 按钮 | 租户生命周期/IAM 转换和支付目录；不再拥有商品或物流规则写权限 |
| 新商城平台权限目标 | 15 组 / 45 页 / 159 按钮 | 在原商城权限基础上接收商品资料及物流规则的 8 页、24 个按钮 |
| 按钮权限合计 | **171 个按钮** | 目标分配 12 + 159；新系统必须以后端权限为准，不能只控制按钮显隐 |

本文只定义兼容范围和验收条件，不授权生产写入、数据迁移、部署或切流。

### 当前实施边界

MSS 兼容层源码分配为商城平台 50 个资源、租户平台 1 个支付资源，51 个资源全部
禁止通用新增、修改和删除。七个商品/物流资源已通过源码中的前向路由和权限迁移
改变归属，但这些迁移尚未在任何环境执行或部署，旧数据按租户转换也仍待演练。
下文的 CRUD、按钮和写操作描述是旧系统能力清单及待恢复验收要求，不代表当前
接口已经可写。

恢复任一写操作前，必须按资源、按操作恢复并验证旧校验、关联和租户约束、模型
Hook、副作用、后端授权、冲突/幂等以及删除语义。此前对本地
`show_categories` 的创建/更新发生在该风险被完整识别之前，只是探索和问题发现
证据，不是当前写能力验收通过。31 个场景仍关闭 0 个。

`system_configs.metadata` 含嵌套 AppSecret，除响应递归脱敏外，还必须禁止作为
全文搜索、`exact`/`contains`/`icontains` 过滤或排序字段，避免结果条数成为秘密
存在性旁路。

## 2. 平台与模块归属

旧后台把控制面和商城数据面混在一个前端中。重构后必须按以下边界拆分：

| 旧领域 | 旧页面/能力 | 新归属 | 建议模块 | 存量兼容要求 |
| --- | --- | --- | --- | --- |
| 登录与系统管理 | 登录、管理员、角色、菜单、按钮、操作日志 | MSS Admin 原生能力 | MSS IAM；增加 `role_scope` 业务扩展 | 管理账号和旧角色可迁入 MSS；旧 `tenant_id`、`warehouse_ids`、`real_warehouse_ids`、`system`、`erp` 数据范围必须保留 |
| 租户生命周期 | 平台列表、域名、移动端 Tag、到期时间、ERP 开关 | 租户平台 | `tenant_lifecycle` | 旧租户 ID 作为外部兼容标识保留；租户期望状态由控制面记录，商城请求不得选择 schema |
| 旧中央物流 | 澳洲物流、中国物流、打包规则 | 商城平台 | `logistics_rule` | 将旧全局快照按租户保留 ID 导入；此后租户维护自己的物流和打包规则 |
| 中央支付 | 中央支付方式 | 租户平台 | `payment_catalog` | 保留中央支付 ID 和业务类型；密钥不得明文回显 |
| 旧中央商品资料 | 分类、品牌、类别属性、商品资料 | 商城平台 | `catalog_master` | 将旧全局快照按租户保留 ID 导入；商品资料和分类层级均由该租户维护 |
| 商城配置 | App 配置、商城名称、默认发件人、订单前缀、版本信息 | 商城平台 | `mall_settings` | 兼容旧配置键；AppSecret 等敏感值改为只写/掩码读取 |
| 商城商品 | 商品领用、显示分类、本地商品、组合商品、价格、库存、上下架 | 商城平台 | `catalog` | 业务模块直接适配旧表、主键、状态和关联；不得把旧数据复制到一套同义新表后长期双写 |
| 发货仓 | 仓库、币种、地区、自提、物流/支付/实物仓关联 | 商城平台 | `shipping_warehouse` | 保留旧仓库 ID 及管理员仓库数据范围 |
| 商城物流 | 物流安装、模板和运费参数 | 商城平台 | `logistics_install` | 兼容旧安装、模板及包裹关联关系 |
| 商城支付 | 支付安装、终端和收款参数 | 商城平台 | `payment_install` | 兼容在线、余额、凭证三类支付语义 |
| 客户 | 会员等级、客户、推荐人、寄件人、收件人 | 商城平台 | `member`、`address_book` | 保留客户、等级和地址簿主键；密码只迁移可安全验证的哈希，不回写明文 |
| 营销 | 满减、包邮、满赠、定向券、新人券 | 商城平台 | `promotion` | 保留活动范围、有效期、会员等级、仓库和商品关联 |
| 首页内容 | 广告、功能圈、首页弹窗 | 商城平台 | `content_slot` | 保留图片、视频、外链、分类、商品、优惠券等跳转类型 |
| 订单 | 自提、待付款、待发货、已发货、已取消、包裹和物流 | 商城平台 | `order` | 兼容旧订单、包裹、付款、物流和备注关系；状态迁移必须事务化并拒绝非法跳转 |
| 财务 | 余额、金豆、提现审核 | 商城平台 | `wallet` | 金额精度、币种、流水方向和关联单据保持一致；取消采用可审计的冲正语义 |
| 进销存 | 实物仓、采购入库、期初盘点、线下销售、库存流水 | 商城平台 | `inventory`、`offline_sales` | 兼容旧库存与流水表；库存变化和业务单据必须在同一事务中落库 |
| 报表 | 销售、采购、库存汇总和明细 | 商城平台 | `reporting` | 报表应从兼容后的业务数据重算，不另建不可追溯的事实来源 |
| 文件与批处理 | 图片上传、分类/价格/物流/订单/库存 Excel 导入导出 | 商城平台 | `import_export` | 导入需校验、可重试、可追踪，重复提交不得制造重复业务行 |

租户平台维护租户生命周期和支付目录。商品资料与物流规则属于每租户商城平台，
旧全局数据只作为一次性、可重放的转换输入；平台可以编排并观察迁移，但不能成为
跨租户商品/物流编辑器。商城仍通过稳定 ID 兼容旧商品、物流安装和业务关系。

## 4. 主业务流程

### 4.1 商品到可售

1. 数据转换为每个租户导入旧分类、品牌、属性和商品资料，保留稳定 ID。
2. 租户在自己的商城平台维护商品资料，并建立显示分类和可售商品。
3. 配置 SKU/组合、发货仓、币种、零售价、会员价、库存和支付方式。
4. 配置物流安装、运费模板和支付安装。
5. 商品启用并上架；置顶、下架、禁用均保留旧状态语义。

### 4.2 客户与营销

1. 建立会员等级及其折扣、默认等级、支付方式和物流选择能力。
2. 建立客户、推荐关系、寄件人和收件人。
3. 配置满减、包邮、满赠活动，按仓库、等级、分类或商品限定范围。
4. 配置定向券或新人券，并完成发放、核销前状态检查和撤回。
5. 广告、功能圈和弹窗按图片、视频、外链、分类、商品或优惠券入口展示。

### 4.3 订单与履约

- 普通订单主状态：`pending -> already -> shipping`，允许按业务规则进入 `canceled`。
- 自提订单主状态：`need-verify -> pending/already`，审核拒绝进入作废/取消语义。
- 订单操作覆盖付款、包裹拆分、包裹数量、重量、物流切换、物流号、面单打印、手动推单、批量发货、寄收件人修改以及操作/财务/包裹备注。
- 状态、库存、余额/金豆和业务流水必须在事务边界内一致；非法或重复状态转换必须拒绝或幂等返回。

### 4.4 采购、库存与线下销售

1. 创建实物仓和采购入库单，记录供应商、币种、单价、数量和付款信息。
2. 入库或期初盘点形成库存流水。
3. 线上订单和线下销售扣减相应实物仓库存。
4. 取消/退回通过反向流水恢复库存，不直接抹除历史。
5. 任一时点满足：`期初 + 采购入库 - 线上出库 - 线下出库 ± 回滚 = 当前库存`。

### 4.5 财务与报表

- 余额支持 AUD/CNY，金豆支持充值、消费、提现、奖励和退款语义。
- 提现审核保存审核结果和凭证，但不向无权限用户回显敏感数据。
- 销售、采购、库存汇总必须能由明细和业务流水重算，不能依赖不可追踪的手工汇总值。

## 6. 明确不照搬的旧缺陷

以下内容是旧实现缺陷或占位，不作为“兼容旧功能”的验收依据：

1. `OrderRefund` 只存在于权限树，运行路由被注释，退款页面为空。若新增退款业务，必须另行定义状态机、财务和库存验收场景。
2. `GoldBean` 菜单实际复用余额组件，独立页面为空；新系统按金豆业务语义实现，不复制空文件结构。
3. 提现审核的“上传凭证”权限按钮没有对应处理分支；新实现必须完成真实权限和业务处理。
4. 系统权限树把澳洲物流和中国物流都写为 `/couriers/list`；新权限使用稳定且唯一的权限代码。
5. 父菜单授权会自动放行隐藏新增/编辑页面；新系统不得沿用这种隐式授权。
6. 旧 Dashboard 只有“各种统计表”占位文字，不计为已存在的统计功能。
7. 多个页面残留复制而来的不可达方法、未导入函数和无效删除逻辑；以实际 API、业务数据和本矩阵为准，不复制死代码。
8. 旧按钮显隐仅是前端控制；新后端必须对每个写操作和数据范围强制鉴权。
9. 旧页面可直接编辑或回显 AppSecret、`app_key`、`app_secret`、token 等敏感字段；新系统不得明文回显或记录这些值。
10. 不能因为表结构简单、存在软删除字段或本地通用编辑成功，就把旧业务表判定为
    “安全 CRUD”；每个写操作必须恢复并验证完整旧语义。

## 7. 生产只读边界

- `r1shop-prod` 正在承载真实客户流量，生产 TimescaleDB `timescaledb-r1shop-prod` 和 Redis `redis-r1shop` 均为实时资源。
- 在用户没有针对当前会话中的具体资源、具体动作明确批准之前，禁止对生产执行任何 DDL、DML、迁移、回填、删除、截断、部署、扩缩容、配置修改或 Redis flush。
- 本矩阵只授权代码和开发环境实施。生产环境仅允许只读检查，例如查询 schema、行数、索引、约束、只读日志和健康状态，并且不得输出密码、Secret、令牌、私钥或完整连接串。
- 当前 51 个 Admin 兼容资源在本地、开发和生产配置中都保持只读；环境切换不能
  绕过逐资源写入资格门槛。
- 所有迁移演练只能在隔离的 `mss-shop-dev` PostgreSQL 上执行；原
  `r1shop-dev` 只能作为固定只读来源。目标数据库中的 `orders` 和
  `order_goods` 只创建表结构、保持零行，除非用户明确改变该规则。
- 每次开发数据迁移都要记录迁移前后逐表行数、金额合计、外键或等价关系、失败检查点和回滚结果。
- GitHub Actions 可以构建镜像，但不得自动部署 Kubernetes；生产和 Cloudflare 发布均需单独批准。
